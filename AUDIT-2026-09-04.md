## Executive summary

Security posture and type safety are in good shape. The critical and high-severity items from the
August pass are genuinely closed — verified in the tree, not taken on trust from the previous
document (see [Closed since August](#closed-since-the-august-pass)).

What is broken now sits one layer out, in correctness and in the safety net:

1. **Eight API error paths return `200 OK`**, so a failed donation renders the success screen to
   the donor.
2. **The two payment test suites are `describe.skip`'d** — the tests that assert exactly the
   status codes broken in (1).
3. **`pnpm test` is red on a clean checkout, and CI never runs it.**

Counts by severity: **1 Critical, 3 High, 4 Medium, 3 Low.**

### Fix in this order

The sequence matters: F2 restores the tests that prove F1, and F6 is what stops the pair from
silently regressing again.

| #   | Item          | Effort  | Why here                                                          |
| --- | ------------- | ------- | ----------------------------------------------------------------- |
| 1   | F1            | ~20 min | Donors see a success screen for payments that never started       |
| 2   | F2            | ~1 h    | 680 lines of status assertions that already cover F1              |
| 3   | F3 · F4       | ~15 min | One helper: greens the suite and removes a site-wide crash mode   |
| 4   | F6            | ~30 min | Nothing above holds without it                                    |
| 5   | F5            | 1 min   | Un-shadows the crawler rules added on 7 Aug                       |

## Findings

### 🔴 F1 (Critical) — Every API error path returns HTTP 200, so failed donations render the success screen

`Response.json(body, init)` takes the status in its _second_ argument. Eight call sites pass only
one, so the status object becomes the response body and the HTTP status stays `200`.

```ts
// app/api/donate/route.ts:17
return Response.json({ status: 429, headers: { 'Retry-After': String(retryAfter) } });
//                   ^ this is the body. The response is 200 OK.

// app/api/member-projects/route.ts:47 — the correct form, same repo
return Response.json({ error: 'Too many submissions.' }, { status: 429, headers: { … } });
```

**Impact.** `components/contribute/DonationWidget/index.tsx:119` branches on `!response.ok`. That
is never true, so a rate-limited, malformed, or EasyPay-rejected donation falls straight through
to `setCurrentStep(5)` — the "done" step — carrying `{status: 429}` where the Multibanco entity
and reference should be. The donor is told the donation worked and given no reference.

`components/members-corner/SubmitProjectForm.tsx:93` has the same shape: a Zod validation failure
returns 200, so the form renders `form.success_title` while nothing was written.

Two sites in these same files already do it correctly, so this is a slip rather than a convention
— which also means a lint rule won't catch it. Worth grepping for `Response.json({ status:` as
part of the fix.

Call sites:

- `app/api/donate/route.ts:17, 25, 46`
- `app/api/subscription/route.ts:15, 52, 54`
- `app/api/member-projects/route.ts:89, 91`

### 🟠 F2 (High) — The payment route tests are switched off

`describe.skip` sits at the top of both payment suites, introduced on 2026-08-04 in
`e31f7766 "work"`. Those are the 31 skipped tests in the run.

- `app/api/donate/route.test.ts:51` — `describe.skip`
- `app/api/subscription/route.test.ts:37` — `describe.skip`

**Impact.** Together they are ~680 lines covering exactly the money paths in F1, and they assert
on `response.status` directly (`expect(response.status).toBe(400)` and friends). Had they been
running, F1 would have failed the suite the day it landed. The EasyPay webhook suite is still
active — only the two outbound payment routes are dark.

---

### 🟠 F3 (High) — The suite is red on a clean checkout, and CI never runs it

12 failures across 5 story files, all one root cause: `transformUrl` throws
`Failed to construct 'URL': Invalid URL` when `NEXT_PUBLIC_APP_URL` is unset.

- `components/shared/ArchiveListComponent.stories.tsx` — via `Pagination`
- `stories/navbar/MobileNavbar.stories.tsx`
- `components/events/list/EventCard.stories.tsx`
- `components/news/list/NewsListComponent.stories.tsx`
- `components/projects/list/ProjectCard.stories.tsx`

**Impact.** The `check` job in `deploy.yml` runs only `pnpm lint` and `pnpm tsc`, so this never
surfaces. It is green only on machines that happen to have a local `.env`. Meanwhile
`.husky/pre-push` _does_ run `pnpm test` — so a fresh clone cannot push without `--no-verify`,
which is the kind of thing that quietly trains people to bypass the hook.

### 🟠 F4 (High) — `transformUrl` hard-crashes without a fallback, unlike its sibling

```ts
// utils/paths.ts:57
const link = new URL(`${process.env.NEXT_PUBLIC_APP_URL}/${lng}${url}`);
if (!searchParams) return link.pathname;

// lib/constants.ts:9 — already defensive
export const BASE_URL = process.env.NEXT_PUBLIC_APP_URL || 'https://hawkstars.org';
```

**Impact.** `patterns.md` mandates `transformUrl` for every internal link, so a missing or
malformed env var takes down every page that renders navigation — not a degraded link, a thrown
exception. It also builds a full absolute URL only to return `link.pathname` and discard the
origin.

Passing `BASE_URL` as the second `URL()` argument fixes the fallback and the redundancy in one
line, and makes F3 disappear with it.

### 🟡 F5 (Medium) — The new robots rules are shadowed by a 2023 static file

`app/robots.ts` was added on 2026-08-07 and disallows `/admin`, `/api` and `/*/preview/`, and
names the AI crawlers. `public/robots.txt` has been there since 2023-11 and disallows only
`/admin/`. Files in `public/` are served ahead of app metadata routes, so the newer rules are not
the ones being served — the CMS preview routes and the API are still advertised as crawlable.

Deleting `public/robots.txt` resolves it. While in there: `app/robots.ts` also carries a stray
second rule, `{ userAgent: 'GPTBot' }`, with no directives attached — it does nothing, and GPTBot
is already covered by the first rule's list.

_(Worth confirming the precedence on staging after the change; the fix is the same either way.)_

### 🟡 F6 (Medium) — CI gaps let each of the above through

Four separate holes in the pipeline, all small:

- `deploy.yml` — the `check` job runs no `pnpm test`, no `pnpm format`
- `deploy.yml:6` — `pull_request: types: [opened]`; add `synchronize` so pushes to an open PR are
  re-checked
- `.husky/pre-push` — calls `pnpm tsc`, bypassing the 4 GB heap that `pnpm typecheck` sets
- `db-backup.yml:46` — `appleboy/ssh-action@master`, a moving branch, on the workflow that holds
  the SSH key
- `deploy.yml:57, 210` — `appleboy/ssh-action@v1`, `chromaui/action@latest` unpinned

The `@master` pin is the one worth doing first: that workflow gets the production SSH
credentials, and a compromised upstream tag would inherit them. Pin the three third-party actions
to commit SHAs; the `actions/*` and `pnpm/action-setup` ones are first-party and fine on tags.

### 🟡 F7 (Medium) — Prettier is failing on files that tooling regenerates

All three drifted files are generated, not authored: `app/(payload)/admin/importMap.js` and
`payload-types.ts` come from `pnpm payload:regenerate`, and `public/mockServiceWorker.js` from
MSW.

Running `format:fix` is the wrong fix — the next regenerate undoes it and the gate goes red
again. Add all three to `.prettierignore`, which currently lists only directories and `*.md`.
That is also what makes it safe to add `pnpm format` to CI in F6.

> This is live in the working tree right now: `importMap.js` and `payload-types.ts` have both
> been dirty since before this audit, purely from regeneration churn.

### 🟡 F8 (Medium) — 22 transitive advisories, all inside the admin panel

`pnpm audit --prod` reports 18 moderate and 4 low. 18 of them are `dompurify`, reached only
through `@payloadcms/ui → @monaco-editor/react → monaco-editor`. The rest are `qs`,
`@opentelemetry/core` and `uuid`.

Exposure is limited to authenticated admin sessions, and the `uuid` advisory covers v3/v5/v6 with
a `buf` argument — this app only calls `v4`. Nothing here is reachable by a site visitor.
Resolution depends on Payload bumping its own tree, so track it rather than force-resolving: a
manual override of a Payload-pinned transitive is more likely to break the admin build than to
help.

### ⚪ F11 (Low) — The rate limiter is correct today and silently wrong after a scale-up

`utils/rateLimit.ts` is a module-level `Map`, which is right for the current single PM2 fork and
is documented as such in the file header.

It becomes a per-worker limiter — effectively N× the intended limit — the moment
`ecosystem.config.cjs` moves to cluster mode, with no error to signal it. Worth a comment in
`ecosystem.config.cjs` at the `exec_mode` line so the constraint is visible from the place that
would break it.

## Closed since the August pass

Verified in the current tree, not carried over from the previous document.

- **SEC-C1** — `member_projects` is locked down: `create: authenticated`, field-level access on
  `is_confirmed` (`create: () => false`, admin-only update), and the public route forces
  `is_confirmed: false` under `overrideAccess`.
- **Contribution PII** — read, create and update now behind `validateContributionAccess`; the
  public site reads through the Local API, so nothing regressed.
- **Stored-XSS vector** — Media uploads narrowed from `image/*` to a raster allowlist, closing the
  SVG path.
- **Webhook auth** — the EasyPay route requires `x-webhook-token` and fails closed when the secret
  is unset.
- **Rate limiting** — added to all four public POST routes; `getClientIp` correctly prefers
  `x-real-ip` and takes the _last_ XFF entry.
- **QUA-H1** — `migrationDir` is set and four migrations are present.
- **QUA-M4** — zero `console.*` calls remain across the app; 12 sites now route through
  `captureSentryMessage`.
- **SEO** — canonical and hreflang are wired through `utils/metadata.ts`; `app/robots.ts` exists
  (see F5); the sitemap batches its six queries with `Promise.all` at `depth: 0`.
- **PERF-H1** — `inlineCss` is now off in production.
- **Type safety** — `strict` holds; only 10 `eslint-disable`/`any` sites across ~630 files, each
  with a stated reason.
