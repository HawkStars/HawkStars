## Method

This audit was built **from the current source only**. The existing `AUDIT.md` (2026-09-10) was excluded from the tree handed to every analysis pass, no prior finding IDs were carried over, and no prior conclusion was reused. For full transparency: its executive summary was read at the outset while scoping this work, which is why the "Fixed since the previous pass" section below can exist at all — but no analysis pass saw it, and every finding here was independently derived and then independently verified against the code. Where a finding here matches an old one, the code produced it again independently — and several old findings are *absent* here because they are genuinely fixed (see "Fixed since the last pass").

Four parallel passes read the code directly. Every finding carries a `file:line` that was actually opened. ## Trust model

*Updated 2026-09-16: the Editor tier was removed. Severities below are rated against this model.*

**Every Payload account belongs to a person associated with the NGO.** There is no public sign-up, no member self-registration and no end-user account system — accounts exist only because an admin created one (`Users.access.create: authenticatedAdmin`). Payload is a workplace tool for NGO staff and volunteers, not a customer-facing application. Two tiers:

| Tier | Flag | Scope |
| --- | --- | --- |
| **User** | none | Signs in to `/admin`. Creates, edits and **publishes** all content. Cannot delete anything, and cannot see users, settings or donations. |
| **Admin** | `isAdmin` | Everything above, plus deletes on every collection, users and roles, settings, contributions and the activity log. |

The dividing line: **destructive and sensitive operations are admin-only; everything editorial is open to every account.** Deletion is permanent here — no soft-delete, no trash, no audit trail — which is why it sits on the admin side even though editing does not. `isEditor` and `authenticatedEditor` were removed: with two tiers they were identical to `authenticated` and implied a distinction that did not exist. `.claude/access-control.md` is the canonical version.

What it means for the findings below:

- **A logged-in user is not an anonymous attacker.** "Any authenticated user can do X" is not remotely exploitable by the public, and findings are rated accordingly.
- **It does not make access control optional.** Three reasons survive the trust assumption: *accidental* damage (an irreversible delete by someone who did not need the button), *account compromise* (a phished volunteer holds a 30-day `Lax` session and `'unsafe-inline'` is in the CSP, so one bad login is a site-wide problem), and *data minimisation* for donor and subscriber personal data, which under GDPR applies inside the organisation as much as outside it.
- **The public bar is unchanged.** Anything reachable without a session — the frontend, the REST/GraphQL surface, anything serialised into a page — is held to exactly the same standard as before.

## Executive summary

This is a well-engineered codebase and the list below is long because the sweep was thorough, not because the work is poor. `strict: true` with no escape hatches, zero `@ts-ignore`/`@ts-expect-error`, seven explicit `any` in the whole tree (five of them unavoidable module declarations), zero `console.log`, two TODOs, a 45-block page builder whose slugs and renderer registry are an *exact* 1:1 set match, and translation files with **perfect key parity** across 18 namespace pairs and 900+ keys. Unusually, the code is commented with its own reasoning — `nginx.conf` explains its cache-lock strategy, `utils/rateLimit.ts` documents the `X-Forwarded-For` bypass it fixes, `app/sitemap.ts` explains exactly which collections carry `_status` and why. A striking number of findings below exist because that reasoning was written down in one place and then not applied in the next one over.

Most of what led this report has been fixed. What is left, in order of what would hurt:

**1. `PAYLOAD_SECRET` is still 7 lowercase letters** in `.env`. Not a code change — confirm whether the production GitHub secret carries the same value and rotate it either way. It signs admin session JWTs; 26⁷ is recoverable offline in minutes. ✓

**2. The EasyPay webhook is still not idempotent, and its secret is still unset.** `handleAuthorisationNotification` creates a contribution with no lookup on `transaction_key`, while the sibling confirm path does query first. With the secret unset every callback 401s and nothing is ever marked confirmed; with it set, a retried callback double-counts. The public transparency total is wrong in one direction or the other. ✓

**3. Four page-builder blocks fetch CMS data from the browser.** Agenda, LatestNews, UpcomingHawkEvent and Sponsors are `'use client'` and `useEffect`-fetch the REST API at depth 2 — four extra round trips per visitor, none of it cached, invisible to crawlers, and arriving after hydration as a layout shift. Two side bugs sit in the same code: `client-side/queries/event.ts:61` sends the event query to the projects endpoint, and none of the four pass `locale`, so EN pages get PT content. ✓

**4. The whole Lucide icon set still ships on every route** (PERF-3). Both real fixes are product decisions rather than mechanics — see the finding.

**5. Nothing enforces one `<h1>` per page** when two hero blocks are stacked, and the global `--border` token is still at 1.26:1. Both are design/authoring decisions rather than defects to patch blindly.

Nothing else rated Critical. The payment and public-submission flows are genuinely well defended — rate-limited, zod-validated, `is_confirmed` forced false at four independent layers, the EasyPay webhook using `timingSafeEqual` and failing *closed* when its secret is missing, with tests covering all of it.

## Security

### [High] SEC-3 — `PAYLOAD_SECRET` in the working tree is 7 lowercase letters ✓
- **Where:** `.env` (value not reproduced — it is 7 characters, all `[a-z]`); consumed at `payload.config.ts:63`, `:213`; production value comes from a GitHub secret at `deploy.yml:69`, `:132`
- **What:** This is the HMAC key Payload uses to sign admin session JWTs. `payload.config.ts:63` asserts only that it is *present*, never that it has entropy.
- **Why it matters:** The keyspace is 26⁷ ≈ 8×10⁹ — recoverable offline in minutes from a single captured token, after which anyone can mint a JWT for any user id, including a full admin. This particular `.env` points at `mongodb://localhost:27017` and `api.test.easypay.pt`, so it reads as a developer file; the risk is that the same string was pasted into the production `PAYLOAD_SECRET` secret. That cannot be checked from the repository.
- **Fix:** Confirm the production secret, and rotate it regardless: `openssl rand -base64 48`. Add a boot assertion beside the others at `payload.config.ts:62-73` that the secret is ≥32 bytes.

### [Medium] SEC-7 — CMS-supplied URLs reach `<iframe src>` and `<a href>` with no scheme check
- **Where:** `components/projects/single/ProjectsSingleHero.tsx:155-156`; validator at `payload/collections/HawkProject/HawkProjectPageTab.ts:96-120`; `components/utils/HawkLink/ExternalHawkLink.tsx:19`; link field with no `validate` at `payload/fields/link.ts:100-111`
- **What:** The `videoUrl` validator constrains the value only if it *already* contains `youtube.com`/`youtu.be`; anything else falls through to `return true` at `HawkProjectPageTab.ts:116`. So `javascript:…` is accepted and rendered as an iframe source. `ExternalHawkLink` renders any `link.url` verbatim as an anchor `href`, and the link field carries no validator at all.
- **Why it matters:** Held at Medium under the trust model. The author is a trusted NGO person, so this is not "an attacker plants XSS" — the realistic vectors are a **compromised account** (30-day `Lax` session, `Users/index.ts:33`) and an editor pasting a URL they did not vet. Either way the payload lands on *public, unauthenticated visitors*, which is the bar the trust model does not relax. CSP does not help: `next.config.ts:30` includes `'unsafe-inline'` in `script-src`, which governs `javascript:` navigation, so it executes same-origin — including against an admin browsing the site while logged into `/admin`. The right helper already exists — `utils/paths.ts:121` `isHttpUrl`, applied to member submissions via `validateProjectUrl.ts` — it is simply not applied here. One note that *does* change: `hawk_projects` is `create/update: authenticated`, so today the Normal tier can plant this; fixing SEC-10 narrows the surface to editors but does not remove it.
- **Fix:** `validate: (v) => !v || isHttpUrl(v) || 'Must start with http(s)://'` on `HawkProjectPageTab.ts:96` and on `payload/fields/link.ts:100`; guard `ExternalHawkLink.tsx:19`. For the iframe, use a provider allowlist the way `components/Crowdfunding/VideoEmbed.tsx:18-34` already does.

### [Medium] SEC-8 — The login rate limiter runs on `beforeLogin`, which does not fire for failed logins
- **Where:** `payload/collections/Users/hooks/rateLimitLogin.ts:14-27`, wired at `payload/collections/Users/index.ts:49`
- **What:** The hook throws 429 after 10 attempts per IP per 5 minutes, and its comment (echoed in `ONBOARDING.md:60`) describes it as capping attempts "regardless of which account is targeted". Payload runs `beforeLogin` *after* the password has been verified — a wrong password throws `AuthenticationError` before the hook chain is reached.
- **Why it matters:** The control documented as the defence against credential spraying never executes on the attempts it is meant to block. What remains is the per-account lockout (`maxLoginAttempts: 5`, 24 h `lockTime`), which does nothing against one attempt each against 500 addresses. nginx's `limit_req … burst=60` is far too loose to matter.
- **Fix:** Move the limiter in front of the operation — a `beforeOperation` hook checking `operation === 'login'`, or an nginx `limit_req` zone scoped to `location = /api/users/login`. Confirm Payload's hook ordering before rewriting (see *Not verified*).

### [Medium] SEC-11 — EasyPay webhook: the secret is absent from the environment, and authorisation notifications are not idempotent ✓
- **Where:** `app/api/easypay/route.ts:29-52`, `:133-158`, `:176-208`; `.env` has no `EASYPAY_WEBHOOK_SECRET`; `.env.example:29`; `deploy.yml:86`, `:150`
- **What:** `isAuthorisedWebhook` is correct — it fails **closed** when the secret is unset and compares with `timingSafeEqual` after a length check. But the variable is simply missing from the working `.env`, so in that environment every EasyPay callback 401s. Separately, `handleAuthorisationNotification` unconditionally `payload.create`s a contribution on every authorisation notification with no lookup on `notification.key`, while `POST` deliberately returns `200` on every error path so retries are absorbed silently. The sibling path `updateContributionStatus` (`:184`) *does* query by `transaction_key` first.
- **Why it matters:** With the secret unset, no donation is ever marked `is_confirmed`, so `/transparency`'s public total and the donor wall permanently under-report — a reconciliation failure visible only as a Sentry warning. With it set, a retried or duplicated callback inserts a **duplicate** `Contribution`, and since the public total sums `value` over confirmed rows, the published figure over-reports. Both directions are wrong on a page whose entire purpose is financial transparency.
- **Fix:** Set `EASYPAY_WEBHOOK_SECRET` in every environment and assert it at boot alongside the others. In `handleAuthorisationNotification`, `payload.find({ where: { transaction_key: { equals: notification.key } }, limit: 1 })` first and `update` when a row exists. Add a unique index on `transaction_key`.

### [Medium] SEC-12 — CSP `script-src` allows `'unsafe-inline'`, which is what makes SEC-7 exploitable
- **Where:** `next.config.ts:28-45`, specifically `:30`
- **What:** `script-src 'self' 'unsafe-inline'` (plus `'unsafe-eval'` in dev), no nonce, no hashes. `frame-src` includes a bare `*.google.com`; `img-src` allows all of `https:`. The trade-off is documented in the file (nonces are incompatible with PPR / `cacheComponents`) and the reasoning is sound as far as it goes.
- **Why it matters:** The policy provides no XSS containment for the defects that actually exist here. `'unsafe-inline'` permits `javascript:` URL navigation, so SEC-7 executes.
- **Fix:** Given nonces are off the table, accept that CSP is not the mitigation and fix the injection sinks directly. Separately, tighten `frame-src` to the exact Google hosts embedded and narrow `img-src` from `https:` to the four hosts already listed at `next.config.ts:63-78`.

### [Low] SEC-14 — `BreadcrumbJsonLd` is the one JSON-LD builder without the `<` escape
- **Where:** `components/seo/JsonLd.tsx:84`
- **What:** `dangerouslySetInnerHTML={{ __html: JSON.stringify(schema) }}` — every sibling (`:61`, `:118`, `:173`, `:225`) appends `.replace(/</g, '\\u003c')`. Checked character by character: in JS source `'\\u003c'` is the six literal characters `<`, a valid JSON string escape for `<`, so the escape in the other four **is** correct and does block `</script>` breakout.
- **Why it matters:** Not currently exploitable — `BreadcrumbJsonLd` and `WebPageJsonLd` have zero call sites. But `items[].name` is exactly the kind of value that comes from a CMS title, so the first caller added gets a breakout for free.
- **Fix:** Add the same escape, or extract one shared `<JsonLdScript schema={…}>` so it cannot be forgotten again.

### [Low] SEC-16 — Google Drive folder name is interpolated into a Drive query string
- **Where:** `lib/google-drive/adapter.ts:29-33`, reached from `handleUpload` at `:53-55`
- **What:** `` q: `name='${folderName}' and mimeType='…' and trashed=false` `` with no escaping of `'`.
- **Why it matters:** Stays Low, and the trust model lowers it further in practice: the input comes from an editor, so the realistic failure is not an attack but a folder name containing an apostrophe (`Projeto d'Arte`) breaking the query or silently matching the wrong folder. Worth fixing as a correctness bug more than a security one.
- **Fix:** Escape backslashes and quotes, and validate the field against `^[\w \-]{1,64}$`.

### [Low] SEC-17 — Cloudinary upload failures are swallowed, leaving Media rows pointing at nothing
- **Where:** `lib/cloudinary/adapter.ts:44-46`
- **What:** `handleUpload` wraps the upload in `try { … } catch (err) { Sentry.captureException(err); }` and returns normally, so `file.filename`/`mimeType`/`filesize` are never reassigned.
- **Why it matters:** Payload then creates the `media` document as though the upload succeeded — a broken asset referenced across public pages, with only a Sentry event to show for it, on the site's only image pipeline.
- **Fix:** Re-throw after capturing so Payload aborts the create.

### [Low] SEC-18 — Seed creates a known-credential admin outside production
- **Where:** `payload/seed.ts:26-46`, invoked from `payload.config.ts:276-279`
- **What:** `onInit` returns early when `NODE_ENV === 'production'`, and production is pinned by `ecosystem.config.cjs:28` and `deploy.yml:130` — so production is safe today. Every other environment gets `admin@hawkstars.org` / `changeme123` with `isAdmin: true`.
- **Why it matters:** A staging box, preview deploy or reachable dev instance is a full compromise, and `payload/plugins/index.ts:80` disables TOTP in development while `payload.config.ts:223` disables email, so there is no second factor and no reset path.
- **Fix:** Gate on an explicit `SEED_DEV_DATA=true` rather than on `NODE_ENV`, and generate the password randomly, printing it once.

### [Low] SEC-19 — MongoDB runs without authentication
- **Where:** `.env:5` (`mongodb://localhost:27017/hawkstars`, no credentials); `deploy.yml:133` writes the same URI into production's `.env`; `db-backup.yml:86` runs `mongodump` with no auth
- **Why it matters:** Every process on the VPS, and anything achieving even limited code execution there, has unauthenticated read/write on donations, users and subscribers. A `mongod` bind-address misconfiguration turns straight into remote database access with no second gate.
- **Fix:** Enable authorisation, create a least-privilege application user, and move the credentials into the `DATABASE_URI` secret rather than the literal in `deploy.yml:133`.

### [Low] SEC-21 — Live credentials sitting in the working tree
- **Where:** `.env` (21 populated values), `.env.sentry-build-plugin`
- **What:** Both are correctly gitignored (`.gitignore:29`, `:52`) so neither is in git — but both exist on disk and travel with any copy of the directory. Between them they hold the Payload secret, a Cloudinary API secret, an EasyPay API key, Google OAuth client secrets and refresh tokens for both Drive and Gmail, a Sentry auth token and a shadcn API key.
- **Why it matters:** Any time this directory is zipped, copied to a shared machine, or handed to a contractor or tool, all of that goes with it — which is what happened to produce this audit.
- **Fix:** Rotate `SENTRY_AUTH_TOKEN`, `PAYLOAD_SECRET`, `EASYPAY_API_KEY` and the Google refresh tokens as a precaution, and strip both files before sharing the directory.

### [High] PERF-2 — Page-builder blocks fetch CMS data from the browser, bypassing every cache
- **Where:** `payload/blocks/UpcomingHawkEventBlock/Component.tsx:27`, `LatestNewsBlock/Component.tsx:81`, `AgendaBlock/Component.tsx:173` (two parallel calls), `SponsorsBlock/Component.tsx:19`; transport `lib/payload/client-side/client.ts:15`
- **What:** Four blocks are `'use client'` and `useEffect`-fetch the Payload REST API after hydration, passing no `depth`/`select` — so REST returns depth-2 documents. `fetchAgendaProjects` pulls up to 20 full `hawk_projects` docs, each carrying the whole page-tab, partners and itinerary trees.
- **Impact:** A homepage with an Agenda + LatestNews + Upcoming block costs **four extra browser round trips and four uncached Mongo queries per visitor**, none touching the `'use cache'` layer the rest of the app is built on. All four render `null` until resolved, so the content is invisible to crawlers and arrives after hydration as a layout shift. Two side bugs found while reading: `lib/payload/client-side/queries/event.ts:61` sends the *event* query to `API_CLIENT_PATHS.projects`, and none of these calls pass `locale`, so EN pages get PT content.
- **Fix:** Convert each to a server component fed by a `'use cache'` + `cacheTag(...)` query in `lib/payload/queries/`, matching `getNewsQuery`. Only the presentational `*BlockView` children need `'use client'`.

### [High] PERF-3 — `lib/icon.tsx` still pulls the whole Lucide set into the navbar chunk **[partially addressed 2026-09-15]**
- **Where:** `lib/icon.tsx:1` (`import * as LuIcons from 'react-icons/lu'`), reached from `components/navbar/DesktopDropdown/utils.tsx` → `Navbar.tsx` (`'use client'`), which the root layout renders on every route
- **Addressed:** `next.config.ts` now sets `experimental.optimizePackageImports` for `react-icons/lu`, `/fa`, `/go`, `/pi`, `/gr`, `country-flag-icons/react/3x2` and `date-fns`, which rewrites the *named* barrel imports elsewhere in the codebase into deep per-icon imports.
- **Still open:** it cannot help this file. `import * as` plus a computed property read (`LuIcons[prefixed]`) is un-tree-shakeable by construction — the bundler has to keep every icon because the key is only known at runtime. So ~1,500 icon components still land in the navbar chunk on every route, in both locales, to render a handful of CMS-chosen glyphs.
- **Why it was left:** both real fixes are decisions rather than mechanics.
