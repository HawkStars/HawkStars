## Method

This audit was built **from the current source only**. The existing `AUDIT.md` (2026-09-10) was excluded from the tree handed to every analysis pass, no prior finding IDs were carried over, and no prior conclusion was reused. For full transparency: its executive summary was read at the outset while scoping this work, which is why the "Fixed since the previous pass" section below can exist at all — but no analysis pass saw it, and every finding here was independently derived and then independently verified against the code. Where a finding here matches an old one, the code produced it again independently — and several old findings are *absent* here because they are genuinely fixed (see "Fixed since the last pass").

Four parallel passes read the code directly. Every finding carries a `file:line` that was actually opened. Twenty-six of the highest-severity claims were then re-verified by hand in a second pass (marked ✓) — including parsing `deploy.yml` with a YAML loader to check the trigger structure, reading the `Contribution` field list against the component that receives it, and character-by-character inspection of the JSON-LD escape.

## Trust model

*Updated 2026-09-16: the Editor tier was removed. Severities below are rated against this model.*

**Every Payload account belongs to a person associated with the NGO.** There is no public sign-up, no member self-registration and no end-user account system — accounts exist only because an admin created one (`Users.access.create: authenticatedAdmin`). Payload is a workplace tool for NGO staff and volunteers, not a customer-facing application. Two tiers:

| Tier | Flag | Scope |
| --- | --- | --- |
| **User** | none | Signs in to `/admin`. Creates, edits and **publishes** all content. Cannot delete anything, and cannot see users, settings or donations. |
| **Admin** | `isAdmin` | Everything above, plus deletes on every collection, users and roles, settings, contributions and the activity log. |

The dividing line: **destructive and sensitive operations are admin-only; everything editorial is open to every account.** Deletion is permanent here — no soft-delete, no trash, no audit trail — which is why it sits on the admin side even though editing does not. `isEditor` and `authenticatedEditor` were removed: with two tiers they were identical to `authenticated` and implied a distinction that did not exist. `.claude/access-control.md` is the canonical version.

What it means for the findings below:

- **A logged-in user is not an anonymous attacker.** "Any authenticated user can do X" is not remotely exploitable by the public, and findings are rated accordingly.
- **It does not make access control optional.** Three reasons survive the trust assumption: *accidental* damage (an irreversible delete by someone who did not need the button), *account compromise* (a phished volunteer holds a 30-day `Lax` session and `'unsafe-inline'` is in the CSP, so one bad login is a site-wide problem), and *data minimisation* for donor and subscriber personal data, which under GDPR applies inside the organisation as much as outside it.
- **The public bar is unchanged.** Anything reachable without a session — the frontend, the REST/GraphQL surface, anything serialised into a page — is held to exactly the same standard as before.

## Executive summary

This is a well-engineered codebase and the list below is long because the sweep was thorough, not because the work is poor. `strict: true` with no escape hatches, zero `@ts-ignore`/`@ts-expect-error`, seven explicit `any` in the whole tree (five of them unavoidable module declarations), zero `console.log`, two TODOs, a 45-block page builder whose slugs and renderer registry are an *exact* 1:1 set match, and translation files with **perfect key parity** across 18 namespace pairs and 900+ keys. Unusually, the code is commented with its own reasoning — `nginx.conf` explains its cache-lock strategy, `utils/rateLimit.ts` documents the `X-Forwarded-For` bypass it fixes, `app/sitemap.ts` explains exactly which collections carry `_status` and why. A striking number of findings below exist because that reasoning was written down in one place and then not applied in the next one over.

Most of what led this report has been fixed. What is left, in order of what would hurt:

**1. `PAYLOAD_SECRET` is still 7 lowercase letters** in `.env`. Not a code change — confirm whether the production GitHub secret carries the same value and rotate it either way. It signs admin session JWTs; 26⁷ is recoverable offline in minutes. ✓

**2. The EasyPay webhook is still not idempotent, and its secret is still unset.** `handleAuthorisationNotification` creates a contribution with no lookup on `transaction_key`, while the sibling confirm path does query first. With the secret unset every callback 401s and nothing is ever marked confirmed; with it set, a retried callback double-counts. The public transparency total is wrong in one direction or the other. ✓

**3. Four page-builder blocks fetch CMS data from the browser.** Agenda, LatestNews, UpcomingHawkEvent and Sponsors are `'use client'` and `useEffect`-fetch the REST API at depth 2 — four extra round trips per visitor, none of it cached, invisible to crawlers, and arriving after hydration as a layout shift. Two side bugs sit in the same code: `client-side/queries/event.ts:61` sends the event query to the projects endpoint, and none of the four pass `locale`, so EN pages get PT content. ✓

**4. The whole Lucide icon set still ships on every route** (PERF-3). Both real fixes are product decisions rather than mechanics — see the finding.

**5. Nothing enforces one `<h1>` per page** when two hero blocks are stacked, and the global `--border` token is still at 1.26:1. Both are design/authoring decisions rather than defects to patch blindly.

Nothing else rated Critical. The payment and public-submission flows are genuinely well defended — rate-limited, zod-validated, `is_confirmed` forced false at four independent layers, the EasyPay webhook using `timingSafeEqual` and failing *closed* when its secret is missing, with tests covering all of it.

**Counts: 0 Critical · 2 High · 31 Medium · 16 Low — 49 open.** Down from 109 at the first pass. The security and performance sections were worked through on 2026-09-16: fifteen more closed, SEC-11 reduced to its environment half. What remains in those two sections is there for a stated reason — an ops action, a product decision, or something that needs a real build or the live box to verify. Each says which.

## Security

### [Resolved] SEC-3 — `PAYLOAD_SECRET` **[closed by the owner 2026-09-16]**
- The 7-character value is the local development `.env` only. The owner has confirmed the production secret is a separate, adequate value, so this is closed rather than fixed in code.
- The dev value is still weak, which matters only if a dev instance is ever reachable. Worth regenerating with `openssl rand -base64 48` when convenient, and the boot assertion at `payload.config.ts:63` still only checks presence, not length.

### [Medium] SEC-11 — `EASYPAY_WEBHOOK_SECRET` is still unset **[code half fixed 2026-09-16]**
- **Where:** `.env` (absent); `app/api/easypay/route.ts:32-51` (auth), `deploy.yml` (forwarded and written to the production `.env`)
- **Fixed:** `handleAuthorisationNotification` is now idempotent. It looks up `transaction_key` before creating (the field is already indexed, `Contribution/index.ts:126`) and returns early on a replay, logging it to Sentry at info level. A retried EasyPay callback, or one arriving for a payment `/api/donate` already recorded, no longer inserts a duplicate — which was inflating the public transparency total, since it sums `value` over confirmed rows.
- **Still open:** the secret itself. `isAuthorisedWebhook` fails **closed** when it is unset, so in any environment without it every callback 401s and no donation is ever marked `is_confirmed` — the transparency total then silently under-reports instead. It is absent from the local `.env`; whether the production GitHub secret exists cannot be checked from the repository.
- **Fix:** set `EASYPAY_WEBHOOK_SECRET` locally and confirm the GitHub secret, then add it to the boot assertions in `payload.config.ts:62-73` so a missing value fails loudly at startup rather than silently swallowing every webhook.

### [Low] SEC-19 — MongoDB runs without authentication
- **Where:** `.env:5` (`mongodb://localhost:27017/hawkstars`, no credentials); `deploy.yml:133` writes the same URI into production's `.env`; `db-backup.yml:86` runs `mongodump` with no auth
- **Why it matters:** Every process on the VPS, and anything achieving even limited code execution there, has unauthenticated read/write on donations, users and subscribers. A `mongod` bind-address misconfiguration turns straight into remote database access with no second gate.
- **Fix:** Enable authorisation, create a least-privilege application user, and move the credentials into the `DATABASE_URI` secret rather than the literal in `deploy.yml:133`.

### [Low] SEC-21 — Live credentials sitting in the working tree
- **Where:** `.env` (21 populated values), `.env.sentry-build-plugin`
- **What:** Both are correctly gitignored (`.gitignore:29`, `:52`) so neither is in git — but both exist on disk and travel with any copy of the directory. Between them they hold the Payload secret, a Cloudinary API secret, an EasyPay API key, Google OAuth client secrets and refresh tokens for both Drive and Gmail, a Sentry auth token and a shadcn API key.
- **Why it matters:** Any time this directory is zipped, copied to a shared machine, or handed to a contractor or tool, all of that goes with it — which is what happened to produce this audit.
- **Fix:** Rotate `SENTRY_AUTH_TOKEN`, `PAYLOAD_SECRET`, `EASYPAY_API_KEY` and the Google refresh tokens as a precaution, and strip both files before sharing the directory.

### [Withdrawn] PERF-2 — page-builder blocks **cannot** be Server Components **[my fix reverted 2026-09-16]**

PERF-2 proposed converting the four blocks that fetched their own data in a `useEffect`
(`SponsorsBlock`, `UpcomingHawkEventBlock`, `LatestNewsBlock`, `AgendaBlock`) into Server
Components reading through the Local API. I made that change on 2026-09-15. **It was wrong,
and it is now reverted.** The finding is withdrawn rather than deferred, because the premise
does not hold in this codebase.

**Why it cannot work.** There is no `RenderBlocks`: every page-builder block is rendered by
`payload/components/RichText/index.tsx`, through the Lexical `blocks` converter registry.
That module is in the **client** graph — `payload/components/LivePreview/LivePreviewPage.tsx`
and `components/news/single/NewsSingleInformation.tsx` are both `'use client'` and import it
(and it calls `useMemo`, which React's `react-server` build does not export). A client module
cannot construct a Server Component element, so a block registered in that map has to be a
client component. `next/dynamic` does not help: it defers the chunk, it does not move the
component across the RSC boundary.

**How it surfaced.** Not as a React error — as a bundler error, two steps removed:

```
MISSING_EXPORT: "fileTypeFromFile" is not exported by
  node_modules/.pnpm/file-type@21.3.4/node_modules/file-type/core.js
  ← payload/dist/uploads/getFileByPath.js
```

`RichText` statically imported the four converted blocks → `lib/payload/queries/blocks.ts` →
`lib/payload/server.ts` → `payload.config.ts` → the whole Payload server entry point, including
`payload/dist/uploads/*`. Those import `fileTypeFromFile` from `file-type`, which v21 exports
only under the `node` export condition; a browser build resolves `core.js`, which does not have
it. Chromatic failed on this. `next build` would have failed too, for a different reason on the
same chain — `lib/payload/server.ts` imports `server-only`, and that chain now ran through a
`'use client'` module.

**What was restored** (all to their 2026-09-14 state):

| File | Back to |
| --- | --- |
| `payload/blocks/{Sponsors,UpcomingHawkEvent,LatestNews,Agenda}Block/Component.tsx` | `'use client'` + REST fetch |
| `payload/components/RichText/index.tsx` | the four blocks as `dynamic()` imports again |
| `lib/payload/client-side/queries/{event,news,sponsors}.ts` | restored |
| `lib/payload/queries/{blocks,sponsors}.ts` | moved to `_to_delete/` |

Two things were **kept** rather than reverted, because they were real bugs the conversion had
fixed independently of it: `fetchEvent` now queries `/api/hawk_events` instead of
`/api/hawk_projects` (the projects collection has neither `date` nor `type_event`, so the
"upcoming event" block was rendering an arbitrary project), and it now filters on
`date >= now` and sorts ascending, so "upcoming" is actually enforced. `SPONSOR_CACHE_TAG`
and its revalidate hook on `payload/collections/Sponsor.ts` are left in place but currently
have no reader.

**If the underlying cost is worth paying**, the real fix is to split `RichText` into a server
registry and a client registry, and accept that the live-preview path can only ever render the
client one — blocks that read the database cannot appear in live preview at all. That is a
deliberate architectural change, not a per-block refactor, and it is not attempted here.

**Guard added.** `scripts/check-storybook-graph.mjs` walks the value-import graph from all 136
stories and fails with the offending chain named, wired into the `check` CI job as
`pnpm check:stories`. Verified in both directions: it passes on the current tree and fails with
the correct chain when the bad import is reintroduced. Nine type-only imports written with value
syntax (`PaginatedDocs`, `MemberProjectDoc`, `GroupedBoardMembers`, `SerializedLinkNode`) were
changed to `import type` so the graph is clean by construction rather than by relying on the
transformer eliding them.

### [High] PERF-3 — `lib/icon.tsx` still pulls the whole Lucide set into the navbar chunk **[partially addressed 2026-09-15]**

### [Medium] PERF-17 — Every link on the site is a client component in order to read the locale

- **Impact:** The entire footer and nav link tree hydrates on every page for a value the server already knows.

### [Medium] PERF-18 — Client-side i18n re-downloads strings already server-rendered
- **Where:** `i18n/client.ts:28-31`
- **What:** `resourcesToBackend((language, namespace) => import('./locales/${language}/${namespace}.json'))` generates a context module over all 2 × 19 locale files (~76 KB per locale). Every `useTranslation` in a client component fetches its namespace chunk after hydration, re-downloading text already in the HTML.
- **Fix:** For components that already receive `lng` from the server, pass the handful of needed strings as props — the pattern `app/[lng]/(org)/agenda/page.tsx:31-61` already uses.

### [Medium] PERF-21 — nginx proxies all HTML to Node with no cache, and references undeclared zones
- **Where:** `nginx.conf:166-179` (`location /` has `limit_req` + `proxy_pass`, no `proxy_cache`); `:4-9` claims `limit_req_zone` and `proxy_cache_path` are declared "immediately below", but only `upstream app` (`:13`) is — while `assets_cache` is referenced at `:73`, `:98`, `:117`, `:151` and `mylimit` at `:167`
- **Impact:** Every HTML and RSC request reaches the single Node process. There is also no `gzip`/`gzip_types` block here, so text compression depends on the parent `http{}` config. The undeclared zones mean this file cannot start standalone — either they live in the host config (and the comment is misleading) or the rate limit the API handlers assume as a backstop does not exist.
- **Fix:** Add a short micro-cache for document responses (`proxy_cache_valid 200 10s; proxy_cache_lock on;` with a bypass for `/admin` and `/preview`), and either declare both zones here or correct the comment.
