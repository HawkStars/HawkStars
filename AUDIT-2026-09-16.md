## Trust model

Two tiers, and it is implemented consistently:

| | User (no flag) | Admin (`isAdmin`) |
| --- | --- | --- |
| Content: create, edit, publish | ✅ | ✅ |
| Delete anything | ❌ | ✅ |
| Users, settings, donations | ❌ | ✅ |

Every account is admin-provisioned NGO staff; there is no public sign-up. The
consequence people get wrong is that **`authenticated` *is* the regular tier**,
so it is almost never the right guard for a destructive operation — and the
collections get this right. The two access findings below are both cases where
the guard was never written at all, not cases where the wrong one was chosen.

### OPS-1, resolved in full (2026-09-17)

The zones were declared on the VPS all along, so the finding's severity was
wrong: the config was never unstartable, its values were merely invisible. Both
halves are now addressed — the site config no longer redeclares them, and the
live `/etc/nginx/nginx.conf` is committed as **`nginx.main.conf`** (a reference
copy; CI does not deploy it) so the numbers are reviewable and survive a
re-provision. Actual values: `assets_cache` keys_zone 20m at
`/var/cache/nginx/hawkstars`, and `mylimit` at **10r/s** per IP.

Two things that surfaced from reading it:

- **`limit_req zone=mylimit burst=60` has no `nodelay`.** At 10r/s a burst is
  queued and drained rather than rejected, so a visitor who trips it waits
  instead of getting a 503. That location serves documents and RSC payloads only,
  so this is defensible — it is now written down at the directive either way.
- **`ssl_protocols TLSv1 TLSv1.1 TLSv1.2 TLSv1.3` in the main config.** TLS 1.0
  and 1.1 are deprecated (RFC 8996). It is currently inert, because every server
  block includes `options-ssl-nginx.conf`, which sets `ssl_protocols` at server
  level and overrides it. Worth narrowing anyway so a future server block that
  forgets the include cannot inherit TLS 1.0.

### Storybook browser suite, fixed 2026-09-17

Running `pnpm test` after the fixes produced 33 failures across unrelated story
files — `Failed to fetch dynamically imported module`, plus
`Vitest failed to find the current suite` pointing at an ordinary story export.
None of the named files had anything in common, which is the tell that it is
infrastructure rather than code.

**Cause: a newly-discovered dependency re-running Vite's optimizer mid-run.**
The two stack traces cite the same module at two different browser hashes —
`plugins.Cigb0uSy-CCo-_6B5.js?v=55fd68f4` and `?v=977dad33`. Vite scans entry
points for bare imports up front; one it has not seen is discovered during the
run, which re-optimizes and invalidates every optimized module URL already in
flight. In the dev server that is a page reload; under `vitest --browser` the run
collapses, and a second copy of vitest is what makes `getCurrentSuite()` fail.

The new import was `react-day-picker/locale` in `components/ui/calendar.tsx`,
added for I18N-4 — reached only from `Calendar.stories.tsx` and
`DatePicker.stories.tsx`. It was the sole new bare import in the whole commit.

**Fix:** `optimizeDeps.include` in `.storybook/main.ts` now pre-bundles
`react-day-picker` and `react-day-picker/locale`, with a comment saying to add an
entry whenever a story graph gains a new bare subpath import. The stale
`node_modules/.cache/storybook` (423 MB, holding caches for two Storybook
versions) has to be cleared once for the optimizer to rebuild:

```bash
rm -rf node_modules/.cache/storybook node_modules/.vite && pnpm test
```

## Executive summary

This is a carefully built codebase. `strict: true` with no escape hatches, no
`console.log` in shipped code, two TODOs, perfect translation-key parity across
900+ keys, and — unusually — code that documents its own reasoning: `nginx.conf`
explains its cache strategy, `utils/rateLimit.ts` explains the `X-Forwarded-For`
bypass it closes, `app/sitemap.ts` explains which collections carry `_status`.
A striking number of the findings below exist because that reasoning was written
down in one place and not applied in the next one over, or because a comment
stopped being true after an unrelated change.

**Five things, in the order they will hurt:**

**1. The public REST API is closed to anonymous callers in production, and five
components fetch from it in the browser.** ✔ `payload-totp` wraps *every*
collection's `read` and the first thing the wrapper does is `if (!user) return
false`. It is disabled in development only. So `SponsorsBlock`,
`UpcomingHawkEventBlock`, `LatestNewsBlock`, `AgendaBlock` and `AgendaCalendar`
each fetch `/api/*` from the browser with no credentials, get 403, and the
shared client helper swallows it and returns the empty fallback. They render
nothing, in production only, silently. This is the single highest-value finding
in the report and it explains any "the agenda is empty on the live site but fine
locally" report.

**2. TOTP is not actually enforced.** ✔ `forceSetup` is consulted only inside a
branch that already requires `_strategy === 'totp'`. An account that never
enrolled falls through to the `else` and is protected by a password alone — and
`POST /api/setup-totp` is gated on nothing but "are you logged in" and "do you
already have a secret", so whoever gets there first binds the authenticator.
Custom endpoints (`dashboard-stats`, `sum-contributions`, `activity-log`,
`translate`, `geocode`) sit outside the wrapper entirely.

**3. The rate limiter's stated precondition is false.** ✔ `utils/rateLimit.ts`
says "the app runs as a single PM2 fork process"; `ecosystem.config.cjs` says
`instances: 2, exec_mode: 'cluster'`. Every limit is doubled and
non-deterministic — including `rateLimitLogin`, the brute-force guard on the
admin panel — and all counters reset on every deploy. The nginx limiter that
would back this up references a zone that is declared nowhere in the repo.

**4. The homepage body is not localized.** ✔ `MainPage.layout` has no
`localized: true`, while its own sibling banner fields do and the equivalent
`Pages.layout` does. The most-visited page of a bilingual site renders in
whichever language was saved last, under an `<html lang>` that says otherwise.

**5. MongoDB has no authentication.** Both the app and the backup job connect
with `mongodb://localhost:27017/hawkstars` and no credentials, so
`authorization` is off. The deploy carefully `chmod 600`s the `.env` that
protects the database; the database itself needs nothing.

**Counts: 1 Critical · 10 High · 24 Medium · 14 Low.**

## Security & authentication

### [Critical] SEC-1 — In production, `payload-totp` denies every anonymous request to every collection, and five components fetch from the browser ✔

- **Where:** `payload/plugins/index.ts:72-81`
  ```ts
  payloadTotp({
    collection: 'users',
    forceSetup: process.env.NODE_ENV === 'production',
    ...
    disabled: process.env.NODE_ENV === 'development',
  }),
  ```
  `node_modules/payload-totp/dist/index.js:129-140` wraps **every** collection's
  `create/delete/read/readVersions/unlock/update` (and `:235-242` every global's
  `read/readVersions/update`) in `totpAccess`, and
  `node_modules/payload-totp/dist/totpAccess.js`:
  ```js
  if (pluginOptions.disabled) { return innerAccess ? innerAccess(args) : Boolean(user); }
  if (!user) { return false; }
  ```
- **What:** `disabled` is true only in development. In production the wrapper is
  active on every collection, and the `!user` check runs before anything else —
  so `read: anyone` on `Sponsor`, `HawkEvent`, `Media`, `Partner` and the rest,
  and `authenticatedOrPublished` on `News`/`HawkProject`/`Pages`, are all inert
  over REST and GraphQL. No collection sets
  `custom.totp.disableAccessWrapper`; I checked.
- **Impact:** The public site itself is unaffected — it renders through the Local
  API, which bypasses access control. But five components fetch `/api/*` from the
  **browser**, with no credentials:
  `payload/blocks/SponsorsBlock/Component.tsx`,
  `UpcomingHawkEventBlock/Component.tsx`, `LatestNewsBlock/Component.tsx`,
  `AgendaBlock/Component.tsx` and `components/agenda/AgendaCalendar.tsx`, all via
  `lib/payload/client-side/queries/*`. Every one gets 403. And
  `lib/payload/client-side/client.ts:17` is `if (!response.ok) return fallback`
  — a silent empty array, no Sentry event. So four page-builder blocks and the
  agenda calendar render nothing on the live site and everything in dev, with no
  telemetry. This is also why the `authenticatedOrPublished` draft protection,
  which its own file documents at length, is not what is actually enforcing draft
  privacy in production.
- **Fix:** Decide what the public API is for. Either set
  `custom: { totp: { disableAccessWrapper: { read: true } } }` on the
  publicly-readable collections (so `anyone`/`authenticatedOrPublished` does the
  work it was written to do), or move those five components to server-side
  `'use cache'` queries and stop calling REST from the browser — which is
  independently the better shape. Whichever you choose, make
  `payloadClientQuery` report a non-ok response to Sentry instead of swallowing
  it; that is what turned a hard failure into an invisible one.

### [High] SEC-2 — TOTP is bypassable by any account that has not enrolled, and the enrolment endpoint binds to whoever calls it first ✔

- **Where:** `node_modules/payload-totp/dist/totpAccess.js`
  ```js
  if (pluginOptions.forceSetup && user._strategy === 'totp' || user._strategy === 'api-key') {
      return innerAccess ? innerAccess(args) : true;
  } else {
      if (user.hasTotp) { ... } else { return innerAccess ? innerAccess(args) : true; }
  }
  ```
  and `node_modules/payload-totp/dist/api/setSecret.js:8-19` — the handler's only
  guards are `if (!user)` and `if (user.hasTotp)`.
- **What:** Operator precedence makes the first condition
  `(forceSetup && strategy === 'totp') || (strategy === 'api-key')`, so
  `forceSetup` only ever helps a session that has *already* passed TOTP. A
  password-only session (`local-jwt`) falls to the `else`; if the user has an
  enrolled secret it is correctly denied, but if `hasTotp` is false it passes
  straight through. `forceSetup` is an admin-panel redirect, not an API gate.
- **Impact:** Any staff account that never finished enrolment is protected by a
  password alone, across the whole CMS, REST and GraphQL. Worse, an attacker with
  those credentials can `POST /api/setup-totp` with their own secret — which both
  satisfies TOTP for them and permanently locks the real owner out, because
  `setSecret` refuses once `hasTotp` is true and `Users.update` is
  `authenticatedAdmin`, so a non-admin owner cannot clear it.
- **Fix:** Back-fill enrolment for every existing account out of band rather than
  letting the first caller bind it, and reject non-`totp` strategies for
  login-derived sessions once enrolment is expected. At minimum, require a
  password re-entry for `POST /api/setup-totp` and alert on every enrolment.
  **Check the database first** for accounts with no secret — that determines
  whether this is live or latent.

### [High] SEC-3 — Custom Payload endpoints sit outside the TOTP wrapper ✔

- **Where:** `payload.config.ts:243-274` registers `/geocode`,
  `/sum-contributions`, `/dashboard-stats`, `/activity-log`,
  `/notifications/mark-read`, `/translate`. Each does its own check, e.g.
  `payload/endpoints/dashboardStats.ts:9`:
  ```ts
  if (!user || !user.isAdmin) return Response.json({ error: 'Unauthorized' }, { status: 401 });
  ```
- **What:** `totpAccess` wraps collection and global access functions only.
  Custom endpoints never see it, so a password-only JWT authenticates against
  them — including for a user who *has* enrolled and whose collection reads are
  correctly denied.
- **Impact:** A stolen password with no second factor reads donation totals and
  the full activity log with actor identities, can mark the entire audit log read
  (which then makes it eligible for the retention job's delete), and can use
  `/translate` and `/geocode` as authenticated proxies to `LIBRETRANSLATE_URL`
  and Nominatim.
- **Fix:** One shared guard asserting `req.user._strategy === 'totp'` (or
  `'api-key'`) in production, applied ahead of each handler's `isAdmin` check.

### [High] SEC-4 — MongoDB runs with no authentication

- **Where:** `.github/workflows/deploy.yml:195`
  (`DATABASE_URI=mongodb://localhost:27017/hawkstars`) and
  `.github/workflows/db-backup.yml:86` (`mongodump --uri=` the same).
- **What:** No username, no password, no `authSource`. A `mongod` with
  `security.authorization: enabled` would reject both, so it is off.
- **Impact:** Every local process on the VPS, any SSRF that reaches
  `127.0.0.1:27017`, and any code execution at any privilege level gets full
  read/write on donor records, contribution history, newsletter subscribers and
  the `users` collection. The deploy `chmod 600`s `.env` to protect the secrets;
  the database those secrets guard needs none.
- **Fix:** Enable `authorization`, create a least-privilege user scoped to the
  `hawkstars` database, move the credentials into a GitHub secret and build the
  URI from it in both workflows. Confirm `bindIp` is `127.0.0.1`.

### [Medium] SEC-5 — `/api/payload-jobs/run` is open to the regular staff tier ✔

- **Where:** `payload/jobs/index.ts:6-21` declares no `access` block. Payload
  fills it from `node_modules/payload/dist/config/defaults.js:134-144` with
  `defaultAccess`, which is
  `node_modules/payload/dist/auth/defaultAccess.js`:
  ```js
  export const defaultAccess = ({ req: { user } })=>Boolean(user);
  ```
  consumed at `node_modules/payload/dist/queues/endpoints/run.js:16`.
- **What:** To be precise: the endpoint is **not** anonymous. It is reachable by
  any logged-in account, including the non-admin content tier, and it is not
  wrapped by `totpAccess` either.
- **Impact:** `payload/jobs/cleanReadNotifications.ts:31-41` deletes with
  `overrideAccess: true`, while `Notification` sets `delete: authenticatedAdmin`
  — so a non-admin can trigger a destructive operation the access model reserves
  for admins. The same call fires `importCrowdfundingSupporters` (appends to the
  public donor wall) and `refreshInstagramToken` (spammable against Meta).
- **Fix:** `jobs.access = { run: authenticatedAdmin, queue: authenticatedAdmin, cancel: authenticatedAdmin }`.
  `autoRun` already covers the legitimate path; no human needs this endpoint.

### [Medium] SEC-6 — `lockTime` is in milliseconds, so the account lockout is 86 seconds, not 24 hours ✔

- **Where:** `payload/collections/Users/index.ts:34-35`
  ```ts
  maxLoginAttempts: 5,
  lockTime: 60 * 60 * 24, // 24 hours
  ```
- **What:** Payload treats it as milliseconds —
  `node_modules/payload/dist/auth/strategies/local/incrementLoginAttempts.js:35`
  does `new Date(currentTime + lockTime)`, and the framework default is
  `600000` with the comment `// 10 minutes`
  (`collections/config/defaults.js:138`). `60 * 60 * 24` is 86 400 ms ≈ **86
  seconds** — weaker than Payload's own default, while the comment claims the
  opposite. (`tokenExpiration` on the line above *is* in seconds, which is what
  makes the mistake easy to miss.)
- **Impact:** Roughly 3 500 guesses/day per account instead of 5, against a
  small and publicly guessable set of staff emails. Compounds with OPS-2, which
  doubles the per-IP limiter, and with SEC-7, which lets the regular tier clear a
  lockout.
- **Fix:** `lockTime: 60 * 60 * 24 * 1000`, and fix the comment.

### [Medium] SEC-7 — `unlock` is omitted from the Users access block ✔

- **Where:** `payload/collections/Users/index.ts:14-20` lists `admin`, `read`,
  `create`, `delete`, `update` — not `unlock`. Payload fills it with
  `defaultAccess` (`Boolean(user)`).
- **What:** An omitted operation key defaults to the regular staff tier, not to
  public — but on an auth collection, clearing a lockout is squarely an admin
  operation under this trust model.
- **Impact:** A non-admin (or a compromised non-admin) can clear the lockout on
  an account being brute-forced, erasing `maxLoginAttempts` entirely.
- **Fix:** Add `unlock: authenticatedAdmin`. `users` is the only auth
  collection, so this is the only place it matters.

### [Medium] SEC-8 — The EasyPay webhook confirms payments with no amount or state cross-check

- **Where:** `app/api/easypay/route.ts:213-221`
  ```ts
  await payload.update({ collection: CONTRIBUTION_COLLECTION, id: contribution.id,
      data: { is_confirmed: isConfirmed } });
  ```
- **What:** The authentication half is good — header-based, `timingSafeEqual`,
  fail-closed, with the reasoning written down. Past that gate, `is_confirmed` is
  flipped on whatever row matches `transaction_key`, with no comparison of
  `notification.value`/`currency` against the stored row, no check of the current
  state, no replay window, and no out-of-band re-query — which the file's own
  header comment names as the missing half of the defence. The `payload.update`
  also runs with `overrideAccess: true`, bypassing the field-level access at
  `Contribution/index.ts:116-119`.
- **Impact:** The secret is long-lived, sent on every notification, and written
  in cleartext into `.env` by CI. Anyone holding it can mark arbitrary
  contributions confirmed or unconfirmed, and the figure that moves is the public
  transparency total. A partial capture is also recorded as fully confirmed at
  the originally requested amount.
- **Fix:** Validate the body with zod; require `value` and `currency` to match
  the stored contribution before setting `is_confirmed: true`; refuse to move a
  confirmed row back on a replayed `failed`; re-fetch the payment from EasyPay by
  `id` before confirming.

### [Medium] SEC-9 — `.env.example` documents the webhook secret incorrectly, and a wrong token fails silently forever

- **Where:** `.env.example:26-31` describes `?token=THE_SECRET` on the URL and
  says "If unset, the webhook is still processed but flagged in Sentry" — both
  contradicted by `app/api/easypay/route.ts:32-42`, which reads the

- **What:** Query-parameter delivery was deliberately removed (the code comment

### [High] DATA-2 — Deleting a page never invalidates the `pages` tag ✔

### [High] DATA-3 — The supporter import is a read-modify-write on an unbounded array, and its write calls `revalidateTag` from a cron context

## Operations, CI & deploy

### [High] OPS-1 — nginx references two shared-memory zones that are declared nowhere ✔

- **Where:** `nginx.conf:167` (`limit_req zone=mylimit burst=60;`) and `:73`,

- **Fix:** Declare both above the `upstream` block and delete the comment that

### [High] OPS-2 — The rate limiter's stated precondition is false ✔

- **Where:** `utils/rateLimit.ts:4-8`
  ```
  * The app runs as a single PM2 fork process behind Nginx, so a module-level
  * Map is shared across all requests … If the app is ever scaled to multiple
  * instances this should be moved to a shared store (Redis).
  ```
  contradicted by `ecosystem.config.cjs:17-18` — `instances: 2, exec_mode: 'cluster'`.
- **What:** The `Map` is per-process. Two workers round-robin the listening
  socket, so each keeps its own counters. The app was scaled; the comment was
  never revisited.
- **Impact:** Every limit is effectively doubled and non-deterministic, and this
  is not only the payment endpoints —
  `payload/collections/Users/hooks/rateLimitLogin.ts:20` uses the same limiter as
  the brute-force guard on the admin login, and
  `payload/endpoints/geocode.ts:75` uses it to bound third-party spend. All
  counters also reset to zero on every `pm2 reload`, i.e. every deploy. The nginx
  limiter that would back this up is the undeclared zone above.
- **Fix:** `instances: 1`, or move the login and geocode limits to a shared
  store. At absolute minimum, correct the comment so the next reader is not
  misled.

### [Medium] OPS-3 — `proxy.ts` matches "admin" as a substring ✔

- **Where:** `proxy.ts:9` — `if (request.nextUrl.pathname.includes('admin'))`,

- **Impact:** On a Portuguese site this is a live collision, not a theoretical

### [Medium] OPS-4 — Rollback restores the build directory but not the code, the dependencies or the database

- **Where:** `.github/workflows/deploy.yml:263-269` — the rollback moves
  `.next.prev` back and reloads. By then the tree is already at the new commit
  (`git reset --hard origin/main`, `:172`), `node_modules` is at the new lockfile
  (`:229`), and `pnpm migrate` has already run (`:240`).
- **Impact:** After a failed health check the box runs the *old* compiled pages
  against the *new* `node_modules` and a *migrated* database — a rollback that
  produces a different broken state rather than the last known good one. And if
  `.next.prev` does not exist (first deploy, or a prior run that reached the
  `rm -rf .next.prev` at `:272`), the `if` is skipped entirely and the failing
  build stays live while the job reports failure.
- **Fix:** Capture `PREV_SHA` before the reset and restore code plus
  dependencies inside the rollback branch; write migrations expand/contract, or
  `mongodump` immediately before `pnpm migrate`; add an `else` that stops PM2 and

### [Medium] OPS-5 — Database backups are never validated and a restore is never exercised

- **Where:** `.github/workflows/db-backup.yml:86-89` — the only post-dump check
  is a human-readable `du -h` printed to the log. No minimum-size assertion, no
  dry-run restore, no document-count comparison, and nothing anywhere in the repo
  ever restores a backup. `mongodump` exits 0 on an empty or partially-readable
  database.
- **Impact:** A dump that silently truncates — disk pressure, a mid-dump restart,
  a wrong `DB_NAME` — is uploaded and counted as good, and the 14-day retention
  prune then deletes the good ones behind it. For a site holding donor records
  this is the difference between a backup and the appearance of one.
- **Fix:** `mongorestore --dryRun` against the archive and fail on non-zero;
  assert a minimum byte size; add a monthly job that restores the newest archive
  into a scratch database and asserts collection counts.

### [Medium] OPS-6 — The Drive upload uses `uploadType=multipart` while the comment claims resumable

- **Where:** `.github/workflows/db-backup.yml:103` (`# ----- upload (resumable,
  …)`) against `:108-112` (`…?uploadType=multipart&…`).
- **What:** Google documents multipart for files of 5 MB or less and resumable
  for anything larger. The whole archive is buffered into one request with no
  resume point.
- **Impact:** Works while the database is small and stops working as it grows —
  and combined with OPS-5, the loss is discovered late. There is also no failure

### [Medium] OPS-7 — PM2 has no log rotation, no graceful-shutdown window, and a memory ceiling above a typical VPS

- **Where:** `ecosystem.config.cjs:17-26` — no `error_file`/`out_file`, no
  rotation (the `pm2-logrotate` module is neither installed nor recorded
  anywhere), no `kill_timeout` (default 1.6 s), `max_memory_restart: '2048M'`.
- **Impact:** PM2 appends stdout and stderr forever; on a single-disk VPS that is
  a slow, guaranteed outage that takes Mongo's data directory and the nginx cache

  requests far longer than PM2 will wait.
- **Fix:** Install and record `pm2-logrotate`; `kill_timeout: 10000`;

### [Medium] OPS-9 — The pre-commit hook reformats the tree but never re-stages ✔

## Verified good

Things I or the sweeps examined specifically and found correct. Listed because
an audit that only lists problems misrepresents the codebase.

- **`getClientIp` and X-Forwarded-For.** `utils/rateLimit.ts:84-88` takes the
  *last* entry, which is correct for nginx's `$proxy_add_x_forwarded_for`
  (`nginx.conf:53`) and is not client-spoofable. The logic is right; it is only
  untested and undermined by OPS-2.
- **`rateLimitLogin` survives the TOTP plugin.** The plugin spreads
  `...collection.hooks` and appends only `afterLogout`/`afterRefresh`, so
  `beforeOperation: [rateLimitLogin]` is intact. Using `beforeOperation` rather
  than `beforeLogin` is correct — `beforeLogin` fires only after a successful
  password check.
- **`/api/member-projects` and `is_confirmed`.** Defended in depth: hardcoded
  `false` in the route, `create: () => false` on the field, an admin-only
  `update`, a `beforeValidate` that re-stamps false, and a re-check on update.
  `overrideAccess` does bypass field access, but the payload is built from a
  whitelist.
- **`useMemo` in `RichText` is not a defect.** React's RSC dispatcher implements
  `useMemo`; `useState`/`useRef`/`useEffect` in the same table are
  `unsupportedHook`. The real problem is the async block it registers (FE-1).
- **Suspense discipline under `cacheComponents: true`.** Every route that awaits
  `params`/`searchParams` without `generateStaticParams` uses a non-async shell
  that opens `<Suspense>` first; the handful without their own boundary sit under
  a layout that wraps `{children}` in one.
- **Translation-key parity.** Zero mismatches across 18 namespace pairs. A second
  pass for identical en/pt values returned 25 hits, all legitimately identical
  proper nouns (`Erasmus+`, `Pinhel`, `Jean Monnet`, `Email`).
- **`toIntlLocale` adoption.** Every date and number format in shipped frontend
  code routes through it except the three cases filed above; the two remaining
  raw calls are admin-only.
- **`aria-labelledby` / `aria-describedby` targets.** Every IDREF resolves except
  FE-6. The accordion, FAQ, team, input, textarea and newsletter cases are all
  correctly paired, including the conditional-error ones.
- **Custom control keyboard operability.** Eight `onClick`-on-non-interactive
  candidates, all either genuine wrappers around real controls or fully specified
  widgets. `image-comparison-slider-horizontal.tsx:173-189` is a textbook
  `role='slider'` with key handling and full `aria-value*`.
- **Modal focus management.** The mobile navbar has Escape-to-close, a
  Tab/Shift-Tab wrap trap, `role='dialog'`, `aria-modal`, a translated label, and
  focuses the close button on open.
- **Bypass blocks.** All three sub-sites render `SkipToContent` over a
  `<main id='main-content'>`.
- **Locale-prefix hardening.** Whole-segment matching plus
  `acceptLanguage.languages([...languages])`, so `/ptx/foo` and `/fr/news` cannot
  render with an out-of-range `lng`.
- **Preview routes.** All five return `robots: 'noindex, nofollow'`, gate on

## What was not verified

Stated plainly, because an audit that does not say what it could not check is
worth less than it appears.

- **Nothing was executed against a running application, and the database was
  never contacted.** `tsc`, `eslint` and `prettier` were run for real; no server
  was started, no HTTP request issued, no collection queried. SEC-1 in particular
  is derived from the plugin's source and the access-function contract, not from
  an observed 403 — **confirm it by loading the live site and watching the
  network tab for `/api/hawk_events`** before doing anything else.
- **`next build` could not be run.** `node_modules` was installed on macOS and
  this shell is linux-aarch64, so rolldown's native binding does not resolve.
  FE-1 and FE-5 both want a real build.
- **The Storybook browser test project was not run** — it needs a real browser.
  The three node-environment API suites pass (57/57, in an isolated scratch
  project).
- **Whether any account currently lacks an enrolled TOTP secret**, which decides
  whether SEC-2 is live or latent. Needs a DB query.
- **Whether `mylimit` and `assets_cache` are declared on the VPS.** If they are,
  OPS-1 drops from "nginx will not start" to "unreproducible and unreviewable".
  `nginx -T | grep -E 'limit_req_zone|proxy_cache_path'`.
- **Whether the Node process is reachable directly on :3000, bypassing nginx.**
  If PM2 binds `0.0.0.0` and the firewall does not block it, every rate limit and
  the `X-Real-IP` derivation are bypassable. `ss -tlnp | grep 3000`.
- **Whether `main` is a protected branch and `check` is a required status
  check.** Nothing in the repo records it, and the recent history is direct
  pushes to `main` with messages like `fix`. If it is not required, the entire CI
  story reduces to "runs after the merge, then deploys".
  `gh api repos/:owner/:repo/branches/main/protection`.
- **Whether Mongo auto-indexes `createdAt`/`updatedAt`/`_status`.** This decides
  how bad DATA-4 is for the `-createdAt` sorts specifically. The findings about
  `startDate`/`endDate`/`publishedAt`/`project_type`/`contribution_date` stand
  regardless — those have no index declaration anywhere.
- **Which branch of DATA-3 actually occurs** — whether `revalidateTag` throws and
  rolls the write back depends on whether Mongo is a replica set.
- **Whether autosave floods the notifications collection.** Pages, News and
  HawkProject autosave every 2000 ms and each `afterChange` runs a `notify*` hook
  that creates a notification row. If those hooks do not guard on `_status`
  transitions, an editor typing for ten minutes writes hundreds of rows to the
  one unbounded collection. Read the three `notify*` hooks to settle it.
- **Whether `curl --max-time 20` bounds each retry or the whole loop** in the
  health check. If the latter, the intended 12 × 5 s grace period is silently
  truncated and a slow-booting app is declared dead and rolled back.
- **Multiple `<h1>` from CMS content.** The static composition is clean — no
  route composes two `h1`-bearing components — but the Lexical `h1` node renders
  a real `<h1>`, so whether live pages contain one or several is a content
  question.
- **Contrast over background images**, and **screen-reader behaviour** — no
  rendered-page check, no NVDA/VoiceOver/axe run. All a11y findings are from
  source.
- **Bundle sizes.** No build, so no analyzer. DATA-5 and FE-1 are structural
  certainties from the import graph; any KB figure would be an estimate, so none
  is quoted.
- **`db-backup.yml`'s Drive credentials and folder scoping**, and the
  Cloudinary/Google Drive storage adapters in `lib/`, were not read in depth.
  Note that `disablePayloadAccessControl: true` on the documents adapter means
  document files are served straight from Drive with no Payload check — benign
  while `read: anyone`, worth revisiting if that ever tightens.
